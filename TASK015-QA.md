## Representation and workflow

A herb may have an optional `categoryLinks: string[]` containing exact category names. The field is absent on legacy herbs and never created by rendering, normalization or a no-op save. `obj.props` remains the sole store of property values; no placeholder property is invented. Rendering takes the union of explicit names and legacy property-derived names, groups by category system and displays each category once. Missing system-order entries do not hide links. Empty rows show “inga egenskaper” / “no properties”, retain `[+]`, and offer a localized Remove category link button.

Use the existing Add existing category/property → choose category dialog, select **Keep category linked even without properties**, then **Save assignments**. This separate explicit checkbox keeps legacy property-only assignment and unchanged-save behavior intact. Opening, selecting a category or canceling never creates an association. Once explicitly linked, the checkbox reopens checked and removal of the final property leaves the link. Unchecking it may remove an empty relationship; a draft that would unlink a still-populated category is rejected before any property mutation. The profile unlink button also refuses populated categories rather than deleting their properties.

Create category from a herb now creates the definition and that herb's explicit link in one save, and stays on the herb profile. Category names and all library content remain literal user data. Swedish and English instructions are updated, and six paired keys are added (223 keys per language). Previous Task012/014 documentation describes historical behavior; this task supersedes its empty-category restriction.

## Lifecycle safety and deliberate limitation

The name-based representation uses conservative, reversible deletion semantics: **a category with any explicit herb link cannot be deleted**. This includes herbs in Trash. Restore a trashed herb and unlink it first, or use the existing explicitly confirmed permanent herb deletion if that is independently intended. No automatic unlink, cascading property deletion, hidden migration or permanent relationship loss is introduced.

Renaming updates live and trashed herbs' explicit links, category identity keys, property category references and system category lists in one logical save, preserving order and unknown metadata. Imported dangling links remain visible as unavailable categories with an unlink action. They reserve their names: category creation/rename/restoration cannot reuse a dangling explicit reference and accidentally attach the herb to an unrelated definition. Existing restore collision and stale-action protections remain intact. Ordinary legacy category deletion without explicit links retains its prior property/system-reference behavior.

The tests cover unlink → delete → reuse name on another herb → blocked original restoration → unlink/delete replacement → restore original. The original herb remains unlinked throughout; no inferred explicit link is recovered. This restriction avoids making an irreversible product decision about recovering or discarding links when deleting populated categories. A future automatic-detachment/recovery policy would require an explicit product decision and a richer identity model.

## Import/export compatibility

`validateImportLibrary()` recognizes categoryLinks on object records, including Trash object payloads: when present it must be a string array. Null, booleans, numbers, strings, object records and arrays containing non-strings reject without coercion. Missing fields remain valid legacy exports. Empty arrays, original list order, unknown metadata and mixed old/new herbs round-trip exactly. No migration, deduplication or unrelated graph rewrite occurs. Actual Chromium downloads and reparses a synthetic backup, then imports it with exactly one save; canceled legacy import and invalid records leave complete snapshots unchanged.
